# V2.0 Development Log — Timecard Bot + Odoo Integration

A reference record of the V2.0 effort: what we changed, why, how it works, and
what's left to do on your side. Written so it stays useful after the working
conversation is gone.

- **Release version:** 2.0 (`RELEASE_VERSION` in `cogs/timetracking/db.py`)
- **DB schema version:** 2 (`TARGET_VERSION`) — file is `timetracker.v2.db`
- **Env schema version:** 2 (`ENV_VERSION`) — kept in lock-step with the DB; the whole V2.0 refactor is one version (pre-refactor = 1)
- **Branch:** `Odoo-Integration` (merge to `main` when production-ready)
- **Git state:** most work committed as `V2.0 Timecard System` (dd745c3); the testing tooling + webhook-gating was a follow-up batch on top.

---

## 1. Where we started / the problems

The bot ran per-employee Discord "clock" messages (clock in/out + jobsite
worktime tagged Construction / Service / Office, admin approval flow, weekly
Excel reports) from a single 1,644-line `cogs/timetracking.py`. Two pains:

1. **Views desynced / didn't update reliably.** Root causes: clock state was
   reconstructed by string-matching embed text on restart; every button did
   blocking `sqlite3`/`requests` on the event loop; the whole view was rebuilt
   per click; ids used race-prone `MAX(id)+1`; several buttons/perms were broken.
2. **No real data visibility.** A capable Odoo JSON-2 API client existed but was
   stranded in `test env/` (never called); `odooId` columns were never
   populated; the webhook "security" only proved the *bot* could reach Odoo, not
   that the *request* came from Odoo.

## 2. Locked decisions (the guardrails everything follows)

- **SQLite is authoritative.** The bot works fully with Odoo down or absent.
- **Odoo sync is best-effort** via an outbox/inbox queue; nothing is lost offline.
- **Views render from DB truth** through one `render_clock()` path — never from embed text.
- **Discord-first**; a web clock was deferred (data layer kept web-ready).
- **Office vs Shop are different things** (see §4).
- **Testing = a separate bot app/token**, not a mode switch on one token.

## 4. Feature-by-feature (what & why)

### 4.1 Structured refactor
Single file → package. Async `aiosqlite` layer; **all queries parameterized**
(killed pervasive f-string SQL injection). Atomic rowid ids replaced
`MAX(id)+1`. One `render_clock()` builds embed + buttons from DB state, and
`on_ready` re-attaches views from `punch_clock` rows (not embed text) — this
fixed the view-desync class of bugs. Fixed the broken `EditPunch`/`TIMECARD_ADMIN_ROLE(S)`
issues; consistent `interaction.response`/`followup` usage.

### 4.2 Odoo integration (SQLite-authoritative, best-effort)
- Client moved out of `test env/` into `cogs/timetracking/odoo/client.py`; **no
  import-time side effects**; blocking `requests` wrapped in `asyncio.to_thread`.
- **Outbox** (`odoo_outbox`): every punch/worktime/customer change enqueues a
  job; a `SyncWorker` drains it and writes Odoo ids back. Offline → rows stay
  `pending`; nothing lost.
- Mappings: clock in/out → `hr.attendance`; worktime → `account.analytic.line`
  (timesheets); customers → `res.partner`.

### 4.3 Worktime → Odoo project/task (when Odoo connected)
- **Service**: search shows **open Field Service tasks** for the searched
  customer, `date_deadline` within ±6 months. Pick a *task*; time posts to it.
- **Construction**: search shows the customer's **active projects** (excluding
  Field Service + Office). Pick a *project*; time posts at project level.
- **Office**: no search; posts to a dedicated **Office project**.
- **Offline** → falls back to the local customer list. **No match online** →
  "no open tasks/projects" and stop.
- Worktime timesheet syncs at work-**end** (final hours). `/linkemployee` links
  an employee to their `hr.employee` id (required or sync rows stay pending).
- Schema v3 added `work_time.odooTaskId` / `odooProjectId`.

### 4.4 Office vs Shop (important domain distinction)
- **Office** = a worktime category you *start/clock into* (desk work). A real
  `work_time` punch (`punchType='Office'`), syncs to the Office Odoo project.
- **Shop** = a **calculated remainder** in reports = shift − (service +
  construction + office) − lunch. Lunch = 0.5h deducted once a shift hits 6h
  unless a trusted `lunchSkipable` employee is ignoring lunch. **Not a punch,
  not synced.** (`reports.py`: `tot_shop += shift - lunch - tot_c - tot_s - tot_o`.)

### 4.5 Unified logging (`botlog.py`)
`from botlog import log` / `timecard_log`. Three sinks: **console** (DEBUG when
`DEBUGGING` set, else INFO), **rotating file** (`logs/bot.log`, capped via
`LOG_MAX_BYTES`/`LOG_BACKUP_COUNT` so it can't grow unbounded), and **Discord
channels** (batched, non-blocking). Routing:
- `log` → **BOT_LOG_ID** (general/infra/webhook/errors)
- `timecard_log` → **TIMECARD_LOG_ID** (clock-ins, job starts, punch edits,
  approvals, Odoo sync/reconcile). Falls back to the general channel if unset.

### 4.6 Pull-based inbound reconcile (`inbox.py`) — replaces echo gymnastics
Odoo posts a **pointer** (`{_id}`); the bot **pulls the record from Odoo** and
reconciles idempotently into SQLite. Why this over the `x_studio_recentlyupdated`
flag + time-window list:
- **Echo suppression is free** — if the pulled record already matches local
  state (the bot just wrote it), reconcile is a no-op. No clock skew, no window,
  no second Odoo automation to reset a flag.
- **Minimal Odoo config**; **payload never trusted for content**; **self-healing**
  (missed webhook = stale-until-next-touch; duplicate = no-op).
- Optional `ODOO_BOT_UID` skips echoes before the pull. Schema v4 added the
  `odoo_inbox` queue; an `InboxWorker` drains it.

### 4.7 Versioned DB filenames + auto-upgrade
Live file is stamped `timetracker.v{N}.db`. On startup the bot finds a legacy
`timetracker.db` (or any older versioned file), **backs it up**, renames it to
the current version, and migrates in one collapsed step (pre-refactor **v1 → v2**).
The test bot uses a separate `timetracker.test.v{N}.db` prefix so a test run
can't touch prod.

### 4.8 Edit Punch button (works with or without Odoo)
`ApprovePunch` shows **Approve + Edit** per direction (admin-only). Edit opens a
modal with a **read-only "Current time" reference** field + an editable
**"New time (YYYY-MM-DD HH:MM:SS)"** field pre-filled with the current value.
Submitting updates SQLite, refreshes the approval message + clock, and — if the
punch is Odoo-linked — pushes the correction (creates the attendance or rewrites
check-in/out).

### 4.9 Webhook security: token, not HMAC
HMAC was removed (it protects payload integrity, moot for a pointer the bot
re-fetches, and it needed Odoo-side code you'd have to maintain). Instead:
- **Shared token** (`WEBHOOK_TOKEN`), auto-generated on first startup, checked in
  constant time via `?token=` (query) or `X-Webhook-Token` (header). Rotate with
  **/regenwebhooktoken** (never printed to Discord — read the new value from
  `.env`, update Odoo URLs).
- **Per-model endpoints** `/webhook/odoo/<model>` — the model comes from the
  URL, so the only thing read from the body is an integer `_id`. A hostile
  `_model` in the payload is impossible to exploit.
- **IP allowlist** (optional, off by default; toggle **/webhookallowlist**),
  auto-refreshed with the Odoo host's IP(s) on each API call. Uses
  `CF-Connecting-IP`. Caveat: Cloudflare-fronted Odoo egress may differ from the
  frontend IP you connect to — if it blocks legit webhooks, disable it (token is
  the real auth).

### 4.10 Versioned `.env` (`config.migrate_env`)
Like the DB: reads `ENV_VERSION`, backs up `.env`, applies rename/remove
migrations, then **adds any new keys from `.env.example`** (preserving your
values), and stamps the version. Uses surgical `set_key`/`unset_key` (never a
full rewrite) so secrets are never at risk. First run also creates `.env` from
`.env.example` if missing.

### 4.11 Native testing tooling (`cogs/testing.py`, TESTING=true only)
A **separate bot app/token** on your desktop (with the tunnel), same codebase,
own `.env`, test guild, test Odoo DB, separate `timetracker.test` db, and
**guild-scoped commands** (instant sync). Flow:
1. Prod: `/timecardexportdb` → download `timetracker.v4.db`.
2. Test: `/testimport` (attach it) → migrated + **sanitized** (prod
   channel/message ids, all `odooId`s, both sync queues stripped) → swapped in.
3. `/testsetup` → creates managed channels (persists ids), builds clocks for
   employees who are members of the test guild.
4. `/linkemployee` to link to test Odoo; test the sync.
5. `/testreset` wipes to baseline; `/testteardown` deletes clocks + only the
   channels the bot created.
Every test command is double-guarded (`TESTING` true AND in `TESTING_GUILD_ID`).

### 4.12 Webhook gated on `ENABLE_TIMETRACKING`
The webhook exists only for the Odoo/timecard integration, so the **server**,
the **`webhookadmin` cog**, and **token generation** all run only when
`ENABLE_TIMETRACKING=true`.

### 4.13 Bidirectional deletions + Odoo-created worktime
Built on the Studio Many2one `x_studio_shift` (`account.analytic.line` →
`hr.attendance`, env `ODOO_SHIFT_FIELD`):
- **Odoo-created timesheets now reach Discord** — the inbox reads the shift link
  to attribute an Odoo line to its local punch and **creates** the `work_time`.
- **Discord-side delete** — an admin "Delete shift" button on the approval
  message, FK-aware (confirms clearing worktime), removes the approval message
  (no orphaned buttons), logs, and cascades the deletes to Odoo via the outbox.
- **Odoo-side delete** — per-model `/webhook/odoo/<model>/delete` routes → an
  admin **approval** (Discord is truth); reject **restores** the record in Odoo
  through the outbox. Customers archive-or-delete locally (new `customer.archived`,
  hidden from search); `pending_action` persists the approval views across restarts.
- **Gated on the shift field** — if it's missing (no Studio / Odoo offline), the
  `/delete` routes return `503` and create-from-shift is skipped; the client
  re-probes periodically so it self-heals.

### 4.14 Full-fidelity inbound reconcile (admin edits in Odoo round-trip)
Because Odoo has multiple, not-always-technical admins who *will* edit records
directly ("it's there, let me make it right"), the inbox now mirrors **every**
field it stores rather than just hours — so the two systems can't quietly drift:
- **`account.analytic.line` edits** re-sync hours, project (→ re-derived
  `punchType` + `odooProjectId`), task, and customer (`partner_id`). Moving a line
  to a different `x_studio_shift` **re-attaches** the `work_time` to that punch; a
  cleared/untracked link keeps the current punch (never orphaned). **`date` is
  intentionally not reconciled** — `timeStarted` is shift-derived (the punch's
  start), used only to refresh the view + compute `timeSpent` at clock-out, so
  pulling Odoo's date back would desync the worktime from its own shift.
- **`hr.attendance` edits** apply `employee_id` **reassignment** (old + new clocks
  re-render; an unlinked target employee is kept as-is with a warning).
- **Odoo-authored `hr.attendance`** (an admin builds a shift from scratch) is now
  **mirrored into a new local punch** (employee resolved by `odooId`). A
  natural-key **echo guard** adopts an in-flight bot-created punch
  (same employee + check-in, no `odooId` yet) instead of duplicating it.
- Watched-field lists in `WEBHOOK_GUIDE.md` / wiki grew to match
  (`project_id`, `task_id`, `partner_id` added to the analytic-line rule; **not**
  `date`),
  with per-model **Domain** filters documented so shared models
  (`account.analytic.line`, `res.partner`) don't flood the bot. Attribution stays
  Discord-first; inbound mirroring is the safety net. Verified in `verify11`.

### 4.15 Employee archiving (Odoo-driven, keeps history)
Construction temp-worker churn: when someone doesn't work out, archive the
`hr.employee` in Odoo and their Discord clock disappears automatically.
- New `employee.archived` column (folded into the v2 migration + fresh-create,
  guarded like `customer.archived` — still one version).
- `hr.employee` is now a webhook model (**archive-only**: a `hr.employee` update
  route, no `/delete` route — see `DELETE_MODELS` in `services/webhook.py`).
  `inbox._reconcile_employee` reads `active`, maps the Odoo employee to the local
  one via `odooId`, and calls `cog.set_employee_archived`.
- `set_employee_archived` deletes the clock message + nulls the clock pointers so
  they can't punch in, sets `archived=1`, and **keeps every punch/worktime row**
  for payroll/reports. Unarchiving clears the flag (clock is re-created manually
  with `/createclock`). `/createclock` refuses an archived employee.
- Deliberately **not** a hard delete — that would break `punch_clock` /
  `work_time` FKs and destroy reportable hours.
- **One-way demographic pull** in the same reconcile: `name`, phone, and the
  private address (`private_street`/`_street2`/`_city`/`_state_id`/`_zip`, the
  state Many2one stored by display name) flow **Odoo → bot** so the weekly
  report's employee header stays current. Odoo is the system of record for these;
  the bot never pushes them back. Empty Odoo values never blank populated local
  data. Field names are env-overridable (`ODOO_EMPLOYEE_*_FIELD`) for non-standard
  Odoo setups. `payrate` / `lunchSkipable` stay bot-local. Verified in `verify12`.

### 4.16 Safer upgrades + startup review
Hardening around the first-run/upgrade path and exception visibility:
- **Pause after an upgrade.** When `.env` is created/gets new keys, or the DB is
  migrated, the changes are applied and the bot **halts before connecting** with a
  review message (`main._halt_for_review_if_upgraded`). `migrate_env()` returns the
  added keys; `cog._open_db` (migrate-only, sets `db_upgraded`) is split from
  `_ensure_db` (starts workers) so the migration can run without kicking off Odoo
  sync during the review pause.
- **Data is preserved** through `backup->rename->migrate` — verified end-to-end in
  `verify14` (all rows/values/ids survive, the `*.db.backup_*` holds the original).
- **0-byte / schemaless db** is now treated as fresh instead of ALTERing tables
  that don't exist (which crashed + hung the aiosqlite thread).
- **Exceptions always logged** (esp. to the file): cog loads in try/except →
  `log.exception`; `sys.excepthook` + a loop exception handler catch the rest;
  `setup_logging()` runs right after `.env` loads. Fixed the venv launch scripts
  (invoke the venv's Python directly; `py -3.12` was running system Python).
- `.gitignore`: `*.db-wal` / `*.db-shm` / `*.db-journal` / `*.db.backup_*`.
- **Clean shutdown.** `/shutdown` used to log "Bot task was cancelled" but the
  process kept running with the db open — `close_db()` (stop workers + close the
  aiosqlite connection) was never called, and the webhook runner + prompt_toolkit
  CLI thread lingered. `main()` now runs `_shutdown_cleanup()` (close db + webhook
  runner) in a `finally` on every exit path, and the entrypoint flushes logs then
  `os._exit()` as a backstop past any non-daemon thread. Verified in `verify15`
  (db.close terminates the aiosqlite worker thread).

### 4.17 Legacy data flag (go-live safety)
The in-use v1 database has historical/garbage punches (deleted rows, forgotten
clock-outs, unlinked worktime) that must stay **reportable in Discord** but must
**never** reach Odoo Production. New `punch_clock.legacy` column:
- The v1->v2 migration stamps **every migrated punch `legacy=1`** (carried through
  the id-rebuild); new punches are `0`.
- **Sync skips legacy** — `_sync_punch_in/out/edit` and `_sync_worktime` return
  early for a legacy punch, so historical rows physically cannot post to Odoo even
  if touched.
- **The clock ignores a legacy open-punch** (`state.get_current_punch` filters
  `legacy = 0`), so employees start **clocked-out** on go-live and a stale v1
  open-punch can't leak on the next clock-out.
- Reports don't filter `legacy`, so the history stays queryable. Verified in
  `verify18`.

### 4.18 Customer <-> Odoo linking (preserve, don't re-import)
The imported Discord customer list is preserved and linked to Odoo `res.partner`
rather than wiped/re-imported:
- **`/synccustomers`** (go-live) auto-links by **exact name** — one
  `get_customer_list()` fetch, matched in memory; reports linked vs. still-unlinked
  (ambiguous / no-match). One-to-one; skips archived + already-linked.
- **`/linkcustomer`** / **`/unlinkcustomer`** for the spelling-mismatch stragglers
  (autocomplete unlinked-local ↔ unlinked-Odoo / linked-local); **`/unlinkedcustomers`**
  lists what's left. One-to-one enforced at link time. Verified in `verify19`.

### 4.19 Self-service clock refresh
A persistent 🔄 Refresh button on every clock (own row) + **`/refreshclock`**
(own clock; re-creates the message if missing) so employees can fix a stale
display themselves.

### 4.20 More timecard reports (self-service + range)
Extracted a shared `_gather_timecard(db, employee_ids, start, end)` from
`timecardreport` (which now uses it). The weekly report already groups/stacks by
date, so a range "just works":
- **`/mytimecard [week]`** — an employee DMs themselves their own week (defaults to
  the most recent Saturday; ephemeral fallback if DMs are closed). Self only.
- **`/timecardrange start end [group]`** — admin, custom range up to 1 year, one
  workbook with every day stacked per employee sheet; `generate_timecard_report`'s
  header label (D8) generalized from a week-date to any period string. Verified in
  `verify20`.

### 4.21 Schema self-heal (columns added after a v2 stamp)
A db stamped at the current version *before* a later column was introduced (e.g. a
test db created before `legacy` existed) would skip `_migrate_to_v2` and then error
`no such column: legacy` on every sync/clock-render. `_run_migrations` now calls
**`_ensure_columns()`** on every open: it idempotently `ALTER`s in any missing
column from `_EXPECTED_COLUMNS` (with its neutral default — data already at this
version is not historical, so `legacy=0`, still syncs) and requeues any outbox/inbox
rows that had failed with `no such column`. Distinct from `_migrate_to_v2`, which is
the one path that marks migrated v1 rows `legacy=1`. Verified in `verify21`.

### 4.22 All db files under database/
So it's obvious which file is live, every timetracking db file now lives under
`<run-dir>/database/`: the live `{prefix}.v{N}.db` (+ its WAL sidecars) sits
directly there, and superseded versions + timestamped backups go in
`database/archive/`. On startup `resolve_db_path` searches `database/` then the
legacy run-dir root (so existing installs' files are pulled in automatically);
`_open_db` distinguishes a **relocation** (same-version file just being moved in →
no backup, no review halt) from a real **upgrade**, then `archive_stale_dbs`
sweeps leftover versions/backups into the archive. Prefix-scoped, so a prod run
never touches the test bot's `timetracker.test.*` file (and vice-versa); files are
only ever moved, never deleted. Verified in `verify22`.

### 4.23 Soft-detach when an Odoo shift link is cleared
Clearing a worktime's `x_studio_shift` in Odoo no longer just "keeps the current
punch." New `work_time.detached` flag gives worktimes three states:
- **attached** — normal, counts everywhere;
- **soft-detached** (`detached=1`) — the shift link was cleared in Odoo; the row is
  **kept** (same id, same last punch) but excluded from reports (`_gather_timecard`)
  and the clock (`state`), and not attributed;
- re-assigning a shift **re-attaches that same row** to the new punch and clears the
  flag (`_reconcile_analytic_line`).
Only a real Odoo-side **delete** of the line hard-removes the row (existing approval
flow, unchanged). `detached` is added to fresh-create + `_EXPECTED_COLUMNS` (so
existing dbs self-heal). Verified in `verify23`.

### 4.24 In-Discord punch management (no DB browser)
Admins can manage punches after the fact from Discord instead of editing SQLite by
hand (and it works with or without Odoo):
- **`/addpunch`** — manually create a punch (missed clock-in); `YYYY-MM-DD HH:MM`
  times, optional clock-out, optional approval; enqueues the matching Odoo sync.
- **`/editpunch`** — fix an existing punch's in/out time or approval (autocomplete
  of recent punches); enqueues a punch edit.
- **`/deletepunch`** — FK-safe delete of a punch. With linked worktime it opens
  an interactive `DeletePunchFlow` (one dropdown per entry: *delete with punch* or
  *reassign to another of the employee's shifts*, plus Confirm/Cancel). Reassigned
  entries move to the chosen punch (Odoo `x_studio_shift` repointed); the rest are
  removed by `delete_punch_cascade` (which already unlinks the attendance + lines
  in Odoo). 5+ worktime entries fall back to a delete-all/cancel confirm.
- **`/reassignworktime`** — standalone move of one worktime to a different punch
  (shared `reassign_worktime` helper). Synced line → new `worktime`/`reassign` op
  (`_reassign_worktime` → `client.set_timesheet_shift`); unsynced line → re-posted
  so its create links to the new attendance. Detached entries are re-attached.
New shared helpers: `_parse_punch_time`, `_refresh_clock`, and `punch_autocomplete`
/ `employee_autocomplete`. Verified in `verify25`.
- **`/addworktime`** — add a worktime to a punch (type via Construction/Service/
  Office choices, hours on the quarter hour, customer required for
  Construction/Service). Optional **`task`** field autocompletes the customer's
  Odoo tasks, **ranked by planned-start proximity to the punch time**; picking one
  stores `odooTaskId` + `odooProjectId` and enqueues a `worktime`/`create` so it
  syncs (with the shift link). No task → stays local-only.
- **`/editworktime`** — change a worktime's type/hours/customer/**task**. When Odoo
  is connected the edit enqueues a new `worktime`/`edit` job that writes the
  updated hours (+ project/task) to the linked timesheet line — or creates the
  line if a task was just linked to a previously local-only entry.
- **`/deleteworktime`** — remove one entry (reuses `delete_worktime_local`, which
  cascades an Odoo delete when the row was synced).
New helpers: `_hours_to_minutes`, `customer_autocomplete`, `worktime_autocomplete`,
`task_autocomplete`. New Odoo client methods `search_tasks_for_partner`,
`get_task_project`, `update_timesheet`; new sync op `worktime`/`edit`
(`_sync_worktime_edit`). (`/addpunch` already auto-pushes via its `in`/`out` jobs.)
Verified in `verify26` + `verify27`. Worktime reassignment + the delete-review
flow (`reassign_worktime`, `worktime`/`reassign`, `client.set_timesheet_shift`,
`DeletePunchFlow`, `/reassignworktime`) verified in `verify28`.

Webhook is behind a **Cloudflare Zero Trust tunnel** (`cloudflared`) — no port
forwarding, automatic HTTPS, `CF-Connecting-IP` carries the real origin. Public
hostname → `http://localhost:<WEBHOOK_PORT>`.
